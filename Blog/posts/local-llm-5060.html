8GB 显存能跑什么本地模型：一份不太乐观的实测

2026-09-14 Ollama · 量化 阅读约 10 分钟 平台：R5 5600 / RTX 5060 8GB

我买显卡的时候把预算全放在了 GPU 上，选了 8GB 显存的型号。 打游戏、剪片子都没问题，但一碰本地模型就很快发现：显存才是那道墙。

这篇不算评测，只是我自己一台机器上的记录。结论先说：7B 量化是日常能用的甜点， 14B 开始变得难受，而真正让我翻车的不是模型大小，是上下文长度。

测试前提

  • CPU：Ryzen 5 5600，内存 32GB DDR4（双通道）
  • 显卡：RTX 5060，显存 8GB
  • 运行方式：Ollama 默认参数，温度与上下文长度按需调整
  • 速度用生成阶段的 t/s（每秒 token 数）估算，取多次运行的中位感觉
说明

下面的数字都是我在自己机器上跑出来的粗略值，会受到驱动版本、上下文长度、 是否同时开着浏览器和虚拟机的影响。不同机器上差 30% 都算正常，别把它当成标准答案。

结果

规模量化显存速度能不能日常用
3BQ4_K_M约 2.5GB55–70 t/s能。适合摘要、改写、翻译这种"处理文字"的活
7BQ4_K_M约 5.2GB28–36 t/s最佳平衡。写小脚本、解释报错都靠它
8BQ5_K_M约 6.4GB22–28 t/s能，但余量只剩一点，开长上下文就危险
14BQ4_K_M约 9.3GB4–7 t/s勉强。部分层跑到内存里，速度掉得很难受
7B + 32K 上下文Q4_K_M溢出3–5 t/s不推荐，体验比 14B 还差

这里有一个直观的规律：显存占用和速度几乎是反着走的。 只要模型完全装进显存，速度就有个舒服的底线；一旦有层要被丢回内存， 速度会直接掉到原来的十分之一，而且是那种"边想边卡"的掉法。

真正的坑：上下文长度

我一开始只盯着参数量，觉得"7B 才占 5GB，我还有 3GB 可以挥霍"。后来才明白， KV 缓存也要显存，而且它随上下文长度线性增长。

当我把上下文从默认值拉到 32K，准备让它读一整份笔记的时候，情况就变了： 显存被吃满，部分计算回落到 CPU，输出变成了一秒几个 token。 那一刻我甚至怀疑是不是模型有问题，其实只是我在做一件这台机器做不到的事。 

# 实际做过的事，大致是这样
ollama run <模型>
>>> /set parameter num_ctx 32768
>>> 把一整份长文档丢进去，然后等

# 观察到的现象
# 显存 → 吃满，随后开始用共享内存
# 生成速度 → 从 30 t/s 掉到 4 t/s 左右
# 风扇 → 立刻起飞

所以对 8GB 显存来说，一个比较现实的做法是：把上下文控制在 8K 以内， 需要处理长文档就先切块、再分别处理，而不是硬塞。这比换更大的模型有用得多。

我现在的实际用法

  • 固定用 7B Q4 级别作为日常模型，不再追求"更大的参数量"
  • 长文档先切段，让它逐段总结，我再自己合并
  • 跑模型时不开游戏、不跑 AE，否则速度会明显受影响
  • 需要更强的能力时直接切云端，不在这台机器上硬撑

另外一件事也值得说：本地模型真正吸引我的不是"能力比云端强"，而是 数据不出本机、随时可用、不用排队、不计费。 整理私人笔记、处理照片目录、写点小脚本，这些活交给它很合适。

结论

8GB 显存完全可以玩本地模型，只要接受它的边界：

  • 7B 量化是甜点，日常够用，速度不烦人
  • 14B 是极限，能跑但不舒服
  • 上下文长度比参数量更容易把显存吃光，这一条最容易被忽视
  • 打算认真玩本地模型的话，显存容量优先于算力

如果让我重新配一次机器，我大概会为了更大的显存多等一两个月， 而不是先买一张算力更强但显存只有 8GB 的卡。这是这次实测里最贵的一条经验。
